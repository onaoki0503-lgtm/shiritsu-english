## 今回の変更

10月20日の堀安先生の指摘を受け、一般向け申込受付とGoogle認証付き管理画面を**別々のApps Scriptプロジェクト**に分離した。公開用に管理機能・個人情報取得APIは存在しない。先生の作成済みスプレッドシートは継続利用する。GitHub Pages＋GASの既存構成を維持し、基盤を移行しない。

先生宛の公開・管理分離コードはGitHubへ保存済み。先生側のウェブアプリURLは未共有で、実GASでの認証・CORS通信・実メール到達は未検証。現在はサイト内申込へ変更するため、岡本管理の受付専用プロジェクトを準備中。公開承認待ち。

## フォルダ構成

- `Intake.gs` — 岡本管理の新しい独立受付プロジェクト用。Common＋公開受付＋台帳初期化を1ファイルに集約。管理RPCなし。既存の先生用プロジェクトへ混在させない
- `Code.gs` — 公開専用：申込受付・講師宛通知・アクセス記録。GETやreplyリクエストは拒否
- `Common.gs` — 両プロジェクトへ追加する共通関数。補助関数は末尾 `_` でRPC非公開
- `Admin.gs` — 管理専用：本人確認・一覧取得・保存済み申込への返信・通知再送
- `Admin.html` — 管理専用画面。外部JavaScriptを使わず、生徒情報はtextContentで表示
- `browser.test.cjs` — Playwrightによる送信失敗・再送・XSS・画面操作のモック試験
- `security.test.cjs` — GASサービスを模擬した認証・再送・障害の回帰テスト
- `README.md` — 本手順・受入テスト・障害対応

## 4. LPの接続・公開（岡本側）

1. `js/site-config.js` の `publicEndpoint` に公開受付URL、`adminUrl` に管理専用URLを設定する。この2つはURLであり秘密の認証鍵ではない。
2. LPのメール申込はサーバーから `saved:true` と一致する受付IDを受け取ったときだけ完了表示する。未設定・通信失敗では完了表示しない。フォーム内容を保持し、同じ内容を再送すると同じ受付IDを使う。ブラウザにはIDと内容ハッシュのみをsessionStorageに保持し、生徒の連絡先や本文をlocalStorageへ保存しない。
3. 公開 `dashboard.html` は管理用画面への入口に変更済み。問い合わせを取得せず、返信機能も持たない。
4. 代表の公開指示後、GitHubへ反映し、GitHub Pagesの公開結果を検証する。既存案件につきFirebaseへ移行しない。

## 保存・通知・返信の状態と復旧

申込の保存は通知より先に確定する。`saved:true` なら通知の成否にかかわらず受付成功。通知はL列の `sent` / `sending` / `unknown`、返信はN列の同状態で管理し、完了した返信はI列を「返信済」にする。

- `unknown`：送信結果が不明。Gmailの送信済み・受信箱を確認する。通知だけなら、管理画面の確認付き「講師宛通知を再送」を利用できる。申込を増やさず通知のみ送るが、既に届いていた場合は重複通知になり得る。
- `sending`が残る：実行途中で終了した可能性がある。Apps Scriptの「実行数」で処理終了を確認し、最低5分待ってGmailと台帳を照合する。**処理中には状態を変更しない。** 通知が未達と確認できた場合のみ、先生が台帳L列を `unknown` にして管理画面から通知だけ再送する。
- 返信が `sending` / `unknown`：自動再送を禁止する。Gmailの送信済みで対象宛先・本文・日時を照合し、送信済みなら先生がI列を「返信済」、N列を `sent` に整合させる。未送信と確認できた場合のみ、先生がN列を空欄へ戻して返信し直す。Gmailから直接返信した場合も同様に台帳を整合する。
- 保存応答を受け取れなかった場合：入力を変えず、同じタブ・同じ受付IDで再送する。タブを閉じる・sessionStorageを消す・内容を変えると新しいIDになるため、同一人物の全申込を自動統合する仕様ではない。

メール送信と台帳更新は単一トランザクションにできず、メール配送の厳密なexactly-onceは保証しない。曖昧な失敗の自動再送を避け、人が送信履歴を確認する方式。公開受付は1時間30件、計測は1日5000新規ページ閲覧を上限とする簡易全体制限で、IP別制限やCAPTCHAは未実装。増加時は運用を見直す。旧計測の重複行は自動削除せず、新版以降のページ閲覧IDで重複計上を抑制する。
